1 Executive Summary
This case study investigates the architecture and design-pattern structure of rails-room-booking, an open-source
Ruby on Rails hotel/room booking application. The study uses an immutable source baseline rather than treating
the current repository state as an informal reference: the original application is identiﬁed by repository https://
github.com/andrewdsilva/rails-room-booking and commit 5e15551ee646871b4bed32c982fa17da319d3ee3. The
investigation covers the application’s domain model, controllers, Rails concerns, authentication and authorization
mechanisms, payment integration, notiﬁcation integration, and booking lifecycle.
The central methodological decision was to distinguish framework mechanisms and ordinary object-oriented
reuse from application-level Gang of Four (GoF) design patterns. A pattern was conﬁrmed only when its participant
roles, interactions, source locations, and behavioral purpose could be established from the source. This prevents a
common failure mode in design-pattern assignments in which every callback is called Observer, every policy class
is called Strategy, or every wrapper is called Decorator or Adapter.
Under that evidence standard, the baseline contains one clearly conﬁrmed application-level GoF col-
laboration: T emplate Method . The collaboration is the shared CRUD workﬂow implemented by CrudConcern
and specialized by BookingsController, RoomsController, and SettingsController. CrudConcern provides the com-
mon algorithm through actions such as index, show, new, create, edit, update, and destroy; concrete controllers
provide hook methods such as base_class, object_class, strong_params, model_params, use_slug?, set_object, and
redirect_to_show. The use of explicit NotImplementedError extension points further demonstrates that the common
workﬂow is intentionally parameterized by resource-speciﬁc operations.
The second part evolves the design for four realistic requirements: a breakfast package, an airport transfer, room
upgrades, and conﬁgurable cancellation policies. The ﬁrst two are modeled as optional additional services rather
than permanent room attributes. Room upgrade is isolated as a reservation-domain operation. Cancellation is the
strongest case for a new GoF pattern: a CancellationService delegates variable cancellation and refund behavior
to a CancellationPolicy, with concrete policies for ﬂexible, partial-refund, and no-refund rules. This establishes a
genuine Strategy collaboration because the context delegates the same conceptual operation to interchangeable
algorithms. The complete evolved Rails application passed 36 RSpec examples with zero failures, including 30
feature examples and an eager-loading check, after rebuilding the dedicated PostgreSQL test database from all 12
migrations.
The third part reproduces the two conﬁrmed pattern ideas independently in Java, Python, JavaScript, and
C++. The implementations do not attempt to port the entire Rails application. Instead, they preserve the
pattern intent and representative behavior. Eight snippets were executed: four Template Method implementations
and four Strategy implementations. Each passed its speciﬁed behavioral check. Process-level timing used one
warmup followed by ﬁve measured runs, with the median reported. The measured medians show substantial
runtime diﬀerences between languages, but these observations are environment-dependent and are not interpreted
as universal language-speed claims.
LLM assistance was used as an analytical aid for source exploration, candidate pattern discovery, evolution
reasoning, cross-language implementation, and ﬁnal audit. The human-veriﬁcation rule was retained throughout:
an LLM hypothesis was not treated as evidence until checked against source code or executable artifacts. Historical
Prompt 02 and Prompt 03 wording could not be recovered verbatim from the retained records, so this report
explicitly records that limitation rather than fabricating a transcript.
The result is intentionally conservative. The project demonstrates that a smaller pattern inventory can be more
academically defensible than a larger inventory produced by pattern-by-name classiﬁcation. It also demonstrates
that new requirements do not necessarily justify forcing every new class into a GoF pattern: additional services
and room upgrade are primarily domain-modeling/refactoring decisions, while cancellation-policy variation has the
structural and behavioral characteristics required for Strategy.
2 Introduction
2.1 Design patterns and evidence-based identiﬁcation
Software design patterns are reusable descriptions of design structures that solve recurring problems in a context.
Their value is not in assigning familiar names to arbitrary classes; the value lies in recognizing a recurring collabo-
ration and understanding the trade-oﬀs that motivate it. In an academic case study, this distinction is particularly
important because a framework such as Ruby on Rails already provides conventions, lifecycle callbacks, inheri-
tance, concerns, routing, persistence and dependency mechanisms. These mechanisms can resemble design-pattern
vocabulary without necessarily constituting an application-level GoF pattern.
The present study therefore treats pattern identiﬁcation as an evidence problem. A candidate must have recog-
nizable participant roles, interactions between those participants, a behavioral or structural purpose corresponding
to the pattern intent, and source evidence that demonstrates the collaboration. A class name such as Policy is not
enough to prove Strategy; a callback is not automatically Observer; and a concern is not automatically Decorator.

2.2 Case-study purpose
The purpose of the case study is to investigate an existing hotel booking application, identify the patterns that can
actually be defended from source evidence, evolve the design under new requirements, and compare representative
implementations across four programming languages.
The study objectives are:
1. Analyze the architecture of an existing hotel booking application.
2. Identify design patterns actually present in the source.
3. Distinguish genuine patterns from superﬁcial pattern candidates.
4. Evolve the application in response to new requirements.
5. Determine whether new design patterns become justiﬁed after evolution.
6. Implement representative conﬁrmed patterns in Java, Python, JavaScript and C++.
7. Compare the implementations using structural, behavioral and process-level performance evidence.
These are study objectives, not claims that the expected outcomes were known before the investigation.
2.3 Three-part assignment structure
The investigation is divided into three parts. Part 1 establishes a reproducible baseline and performs pattern
discovery. Part 2 introduces new domain requirements and evaluates the resulting design pressure, including a
Strategy-based cancellation-policy design. Part 3 isolates the conﬁrmed pattern collaborations into small executable
examples so that the same design intent can be compared across four languages.
3 Application and Architecture
3.1 Application background
The studied application is rails-room-booking, an existing Ruby on Rails hotel/room booking application. The
baseline source is the public repository https://github.com/andrewdsilva/rails-room-booking at commit
5e15551ee646871b4bed32c982fa17da319d3ee3. The source language is Ruby and the application uses Rails MVC
and Active Record as its main application architecture.
The baseline domain entities established directly from the inspected source are:
• User: authenticated application user and owner of rooms/bookings/settings.
• Room: bookable accommodation with descriptive attributes, capacity, pricing and amenity ﬂags.
• Booking: reservation connecting a user and room, with dates, guests, price totals and cancellation state.
• Setting: user-associated conﬁguration, including V AT used by booking-price calculation.
The baseline source does not establish separate application-owned models for Hotel, Customer, Cancellation, or
AdditionalService. This distinction matters because the case study must not retroactively attribute domain objects
to the application merely because those concepts appear in the assignment statement.

3.3 Architecture overview
The baseline follows the conventional Rails ﬂow:
Figure 1: Baseline Template Method collaboration implemented by Ruby module inclusion. Dashed dependencies
denote include CrudConcern, not class inheritance; controller hooks specialize the shared CRUD skeleton.
At a high level, a browser request reaches Rails routes and a controller. Controllers use Active Record models
and model concerns to access and manipulate persistent state. PostgreSQL stores the application data. Pundit
is used for authorization, Devise for authentication, Payify/Stripe integration for payments, Active Storage for
attachments, and Integromat/Make integration for booking webhooks. Stimulus and Turbo participate in the
front-end interaction model.
The architecture is therefore better described as a Rails MVC/Active Record application with reusable concerns
and integrations than as a collection of GoF patterns. This framing is important because Rails itself supplies
substantial structure.

3.5 Architecture collaborations
3.5.1 User and Booking
The source establishes Booking belongs_to :user and User has_many :bookings. The booking controller also scopes
booking queries by current_user.id. This provides both persistence-level association and controller-level ownership
scoping.
3.5.2 User and Room
The source establishes Room belongs_to :user and User has_many :rooms. This relationship supports room owner-
ship and the room-management scope.
3.5.3 Room and Booking
The source establishes Room has_many :bookings and Booking belongs_to :room. A vailability is checked in
Booking#dates_are_available, where conﬂicting bookings are queried using the candidate booking’s dates.
Room#booked_dates separately exposes future booked date ranges in a display-oriented representation.
3.5.4 Booking and Setting
Pricing behavior is extracted into HasPriceConcern. Its vat method accesses room.user.setting.vat, making the
setting part of the booking-price calculation.

4.3.2 Why this is T emplate Method
The collaboration has the essential shape of Template Method even though Ruby/Rails expresses it through a
module concern rather than a Java-style abstract class.
First, the reusable algorithm is centralized. For example, create performs authorization, constructs an object,
validates it, saves it, and redirects on success; otherwise it renders the form with an error status. The algorithm is
not copied separately into each resource controller.
Second, the algorithm invokes resource-speciﬁc hooks. object_class, strong_params and model_params determine
which resource and parameters participate in the shared lifecycle.
Third, the concrete controllers implement those hooks diﬀerently. Their base_class methods return Booking,
Room, and Setting, respectively; their object_class methods return the corresponding scoped Active Record rela-
tions. SettingsController additionally overrides set_object and redirect_to_show because its resource semantics
diﬀer.
Fourth, the concern contains explicit required extension points. base_class and object_class raise
NotImplementedError in the shared module. This is stronger evidence than mere code reuse: it establishes a
reusable algorithm with designated operations that concrete participants must supply.

5.11 Refactoring analysis
The primary design pressure is responsibility growth. The original Booking model already combines associations,
availability validation, cancellation state, pricing behavior via a concern, payment integration and notiﬁcation
behavior. New requirements would increase this concentration if implemented directly in the model and controllers.
The evolution responds by extracting responsibilities:
• additional-service selection and pricing become explicit domain concepts;
• room-upgrade validation and price adjustment become a dedicated operation;
• cancellation rules become interchangeable policies;
• the existing controller Template Method remains responsible for the common CRUD lifecycle.
The resulting design is not claimed to be universally superior. It introduces more classes and indirection. That
trade-oﬀ is justiﬁed only when the business rules are expected to vary or grow.

6.8 Language-speciﬁc observations
Java. Java makes the pattern contracts explicit through interfaces and abstract classes. Static typing makes
participant relationships visible in declarations, at the cost of more syntactic structure.
Python. Python can express the same abstraction using ABCs, but its dynamic dispatch makes some contracts
less syntactically prominent. The implementation is concise in conceptual terms while retaining explicit abstract
methods.
JavaScript. JavaScript’s class syntax provides a familiar object-oriented surface, but dispatch remains dynamic.
The pattern can be expressed without compile-time interface enforcement.
C++. C++ expresses the abstraction through pure virtual functions and runtime virtual dispatch. The imple-
mentation can also use ownership mechanisms such as shared_ptr for the selected Strategy.

9 Findings and Contributions
9.1 Finding 1 – A single baseline pattern is defensible
The original application contains one clearly evidenced application-level GoF collaboration: Template Method
through CrudConcern and its concrete controllers. This conclusion is narrower than a pattern-by-name inventory
but stronger because the participant roles and calls can be traced directly.
9.2 Finding 2 – F alse positives matter
Several Rails mechanisms resemble classic patterns. However, similarity of vocabulary is insuﬃcient. Pundit policies
are authorization constructs; callbacks are lifecycle hooks; concerns are a Ruby/Rails reuse mechanism; and Payify
is an external payment dependency. None was promoted to a GoF pattern without the required collaboration
evidence.
9.3 Finding 3 – Requirements create diﬀerent design pressures
Breakfast and airport transfer are best understood as optional service domain concepts. Room upgrade is a reser-
vation modiﬁcation workﬂow. Cancellation policy is a variable business-rule family. Treating these requirements
identically would obscure their diﬀerent design pressures.
9.4 Finding 4 – Cancellation is a strong Strategy case
The cancellation requirement creates interchangeable algorithms with a stable context. CancellationService dele-
gates to CancellationPolicy, allowing ﬂexible, partial-refund and no-refund implementations. This is the strongest
new pattern introduced by the evolution.
9.5 Finding 5 – Cross-language mechanisms diﬀer
The same design intent appears through Java interfaces/abstract classes, Python ABCs, JavaScript class-based
dynamic dispatch and C++ pure virtual functions. The pattern concept is therefore more stable than its language-
level expression.
9.6 Finding 6 – Evidence reduces pattern inﬂation
The project demonstrates a general methodological lesson: a defensible design-pattern inventory should be willing
to contain only one baseline pattern when only one collaboration is actually established. Academic quality is
improved by rejecting unsupported candidates rather than maximizing the pattern count.

10 Conclusion
This case study examined an existing Ruby on Rails hotel booking application using a source-ﬁrst, evidence-based
design-pattern methodology. The baseline was ﬁxed to an immutable commit so that the pattern inventory could
be reproduced against a deﬁned source state. The architecture was analyzed as a Rails MVC/Active Record system
with controllers, models, concerns and external integrations.
The baseline result was intentionally conservative: one application-level GoF collaboration, Template Method,
was conﬁrmed. CrudConcern provides a common CRUD algorithm and concrete resource controllers supply resource-
speciﬁc hooks. The source locations, interactions and behavioral purpose support the classiﬁcation. Several other
plausible candidates were investigated but rejected because the required pattern collaboration was not established.
The evolution phase demonstrated that new requirements do not imply a uniform pattern solution. Break-
fast and airport transfer were modeled as additional services. Room upgrade was isolated as a domain opera-
tion. Cancellation policy introduced genuine algorithmic variation and was therefore represented using Strategy.
CancellationService acts as the context and delegates cancellation/refund behavior to interchangeable policy im-
plementations.
The cross-language phase showed that the same design intent can be represented in Java, Python, JavaScript
and C++. All eight representative snippets passed their behavioral checks. Process-level timing measurements
were collected using one warmup and ﬁve measured runs, and the medians were reported. The measurements
demonstrate environmental/runtime diﬀerences but do not establish universal language performance rankings.
The most important lesson is methodological. Design patterns should be identiﬁed from collaborations and
intent, not from names or superﬁcial structural resemblance. Likewise, evolution should introduce a pattern only
when the new requirement creates the problem that the pattern is designed to solve. The resulting architecture is
not claimed to be universally superior: it trades some additional classes and indirection for clearer separation of
variable business rules.
Overall, the case study shows how a real Rails application can be analyzed, challenged, evolved and repro-
duced across languages while maintaining a clear distinction between framework mechanisms, domain design and
recognized GoF patterns.
